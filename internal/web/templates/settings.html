Global settings

Traffic shaping

Smart Queue Management

Fights bufferbloat: without this, a single saturating flow (a big download, a backup) can queue up enough data on the WAN link that latency-sensitive traffic sharing it - a game, a video call - gets stuck waiting behind it, even though those packets are tiny. This applies fair queuing plus active queue management (the cake qdisc) to the WAN link, so no single flow can monopolize it. Applies immediately - no restart needed.

Set both numbers a bit below your actual measured speed (try ~90% of what a speed test shows) - if the numbers are too high, shaping can't do its job, since traffic queues up further upstream (in your modem, at your ISP) before it ever reaches cobweb. Setting them too low wastes bandwidth you actually have.

LAN segments (VLANs)

Routed networks

Each segment gets its own DHCP listener bound to its own interface. Adding or removing a segment here needs a cobweb restart before its DHCP listener actually starts or stops - the interface itself (an 802.1q subinterface for a VLAN, e.g. enp1s0.20) needs to already exist at the OS level; cobweb doesn't create it for you. If a device isn't showing up as expected, check the raw ARP table to see exactly what cobweb sees.

Firewall & port forwarding

Port rules

cobweb can run this box's firewall itself: filtering, NAT masquerade for the LAN segments, and the port rules below, all generated from this page and applied atomically. It owns two nftables tables (cobweb and cobweb_nat) and never touches any other. Off by default.

Forward sends traffic that arrives on the WAN side, at this box's own WAN address on the given port, to a host inside one of your LAN segments - e.g. SMB (445) to a machine in your room, reachable from the house network at this box's WAN IP. Allow to this box lets a WAN-side host reach a service running on this box itself, e.g. a file browser that a reverse proxy talks to. Set a Source whenever you can: a rule without one accepts traffic from every host on the WAN-side network.

Docker containers

Running Docker on this box? Turn this on and cobweb will let the Docker bridges through its firewall: containers can reach the internet, the LAN segments and this box (e.g. the DNS server), and a published port (-p 8080:80) is reachable from the LAN segments and from the WAN side. A container's own address is never reachable directly, only what you publish. Docker's own rules still keep its separate networks isolated. Off by default, and it only matters while the firewall above is on.

VPN (WireGuard)

Running a VPN server on this box (WireGuard's wg0, say)? List its interface here and the people connected through it are treated like a LAN segment: they can reach this box, the LAN segments, the WAN-side network and (if Docker is on) published container ports. Nothing can start a new connection toward a VPN client. Don't forget a rule under Port rules allowing UDP 51820 to this box, and a forward for it on your main router. Off until you add an interface.

Comma or space separated; a trailing * matches any ending (wg*). Names that would also match the WAN, a LAN interface, loopback or a Docker bridge are refused. Whoever holds a VPN key gets full LAN access, so keep the keys private.

Backup & migrate

Export / import config

Everything on this page lives in one JSON file - export it to back it up, or move your whole setup (segments, reservations, DNS records, SQM settings, hostname overrides) to a new machine. Deliberately excludes your login - the admin password lives in a separate file this never touches, so you'll set that up fresh on the new install.

Export config

Importing replaces everything on this page. Double-check you have the right file before uploading - there's no undo. Restart cobweb afterward for segment/DHCP changes to fully take effect.
